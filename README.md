### ᴏᴘᴇɴ ꜱᴏᴜʀᴄᴇ

<br>

**[bosskmk/pluto_grid](https://github.com/bosskmk/pluto_grid)** &nbsp;·&nbsp; 745★ &nbsp;·&nbsp; ![Open PR](https://img.shields.io/badge/PR_%231165-Open-2EA043?style=flat-square&logo=github&logoColor=white) ![Pull Shark](https://img.shields.io/badge/🦈_Pull_Shark-FBBF24?style=flat-square)

**Overview** — A community-maintained Flutter DataGrid for keyboard-navigable, spreadsheet-like tables, used in production apps across the ecosystem.

**Contribution** — [PR #1165](https://github.com/bosskmk/pluto_grid/pull/1165): *"fix: notify listeners on setConfiguration and setTextDirection changes."*

**Technical challenge** — `setConfiguration()` and `setTextDirection()` mutated the grid's internal state without calling `notifyListeners()`. Cells that depend on that notification (Select, Date, directional icons) silently kept rendering stale configuration — most visibly, switching RTL/LTR appeared to only partially update the grid until an unrelated action happened to force a rebuild.

**Solution** — Added listener notifications that respect Flutter's build lifecycle: a direct `notifyListeners()` call for `setConfiguration()` (safe outside the build phase), and a deferred `notifyListenersOnPostFrame()` for `setTextDirection()` (invoked mid-build, where a direct call would trip Flutter's build-phase assertions) — mirroring the package's existing `setKeepFocus()` convention. Added unit tests covering both notification paths.

**Impact** — The fix lives in the package itself, so every application using `pluto_grid` benefits: RTL/LTR switches and configuration changes now propagate to every dependent cell immediately, with no manual refresh.

**Links** — [View PR](https://github.com/bosskmk/pluto_grid/pull/1165) · [Package](https://github.com/bosskmk/pluto_grid)

#### ⚡ Voltify — Smart Energy Management App

`Flutter` `BLoC/Cubit` `GetIt` `dartz` `bloc_test / mocktail`

**Problem** — Give users a clear, real-time view of energy consumption, estimated bills, solar generation, and CO₂ savings in one app.
**Architecture** — Strict three-layer Clean Architecture: `presentation` (widgets + Cubit), `domain` (pure Dart entities, repository contracts, use cases), `data` (repository implementations behind a swappable data source), wired together with `GetIt`.
**My role** — Designed the folder structure and layer boundaries, built the auth feature end-to-end, and set up the testing scaffolding.
**Implementation detail** — Failures are modeled with `dartz`'s `Either<Failure, Success>` instead of exceptions, so every use case has an explicit, typed failure path instead of a try/catch scattered across the UI.
**Challenge** — Keeping the domain layer completely framework-agnostic — no Flutter or Firebase imports below the data layer — so business logic stays portable and unit-testable in isolation.
**Outcome** — A fully mockable backend boundary: the mock data source can be swapped for a real API without touching UI or domain code.

[View source](https://github.com/menna3lwan/Voltify)

#### 🏥 Hen Lehen (هُنَّ لَهُنَّ) — Women-Only Telemedicine Platform

`Flutter` `Firebase` `Supabase` `Provider`

**Problem** — Connect female patients with female doctors across Egypt for online and clinic-based consultations, in a space designed to feel private and comfortable.
**Architecture** — Two independent Flutter apps (patient-facing and doctor-facing) sharing a common domain, backed by Firebase Authentication and Supabase for data and real-time chat.
**My role** — Built the appointment booking, clinic branch management, and real-time medical chat flows for both apps, including full Arabic/English localization.
**Implementation detail** — RTL/LTR layout mirroring is handled through shared layout primitives rather than duplicated per-screen logic, so localization doesn't double the UI code.
**Challenge** — Keeping data models and auth state consistent across two apps and two backend services (Firebase + Supabase) without a shared codebase.
**Outcome** — Two production-shaped apps with role-based dashboards, online vs. clinic consultation flows, and full dark/light theming.

[Patient app](https://github.com/menna3lwan/patient_app) · [Doctor app](https://github.com/menna3lwan/doctor_app) · [Watch demo](https://youtu.be/vsnvrcTbRHM)

#### 📝 Exam App — Elevate Online Exams

`Flutter` `BLoC/Cubit` `Clean Architecture` `Dio`

**Problem** — Give students a reliable client for browsing subjects, taking timed exams, and reviewing results against a real production REST API.
**Architecture** — Feature-first Clean Architecture with BLoC/Cubit for state, GetIt for DI, and the Repository pattern abstracting a Dio-based API layer with centralized result handling.
**My role** — Implemented authentication, exam session/timer logic, results/history screens, and the Dio interceptor layer for token management.
**Implementation detail** — Centralized API error handling means every feature reports failures through the same typed result path, instead of each screen parsing Dio exceptions independently.
**Challenge** — Keeping exam-session state (and the timer) consistent across network interruptions and reconnects.
**Outcome** — A full auth lifecycle, timed exam sessions with scoring, and exam history grouped by subject, shipped on a production API.
