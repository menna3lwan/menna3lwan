<summary><b>⚡ Voltify — Smart Energy Management App (Clean Architecture flagship)</b></summary>
<br>

![Flutter](https://img.shields.io/badge/Flutter-02569B?style=flat-square&logo=flutter&logoColor=white)
![Bloc](https://img.shields.io/badge/Bloc%2FCubit-0175C2?style=flat-square)
![GetIt](https://img.shields.io/badge/GetIt_DI-02569B?style=flat-square)
![dartz](https://img.shields.io/badge/dartz_Either-0175C2?style=flat-square)
![Testing](https://img.shields.io/badge/bloc__test%20%2F%20mocktail-02569B?style=flat-square)

[![Source](https://img.shields.io/badge/GitHub-Source-181717?style=flat-square&logo=github&logoColor=white)](https://github.com/menna3lwan/Voltify)

**Problem:** Give users a clear, real-time view of energy consumption, estimated bills, solar generation, and CO₂ savings in a single mobile app.

**Architecture:** Strict three-layer Clean Architecture — `presentation` (Flutter widgets + Cubit), `domain` (pure Dart entities, repository contracts, use cases), `data` (repository implementations behind a swappable data source). `GetIt` wires dependencies so the mock backend can be replaced with a real one without touching UI or business logic.

**My responsibilities:** Designed the full folder structure and layer boundaries, implemented the auth feature (sign-up/sign-in/sign-out) end-to-end, and set up the project's testing scaffolding.

**Technical challenges:** Keeping the domain layer completely framework-agnostic (no Flutter or Firebase imports below the data layer); modeling failures with `dartz`'s `Either<Failure, Success>` instead of exceptions for predictable, explicit error handling.

**Notable features:** Centralized design tokens (colors, spacing, typography), full form validation, loading/error states, and a test suite built with `bloc_test`, `mockito`, and `mocktail`.

</details>

### [pluto_grid](https://github.com/bosskmk/pluto_grid) · 745★ community-maintained Flutter DataGrid

![Open PR](https://img.shields.io/badge/PR_%231165-Open-2EA043?style=flat-square&logo=github&logoColor=white)
[![View PR](https://img.shields.io/badge/GitHub-View_PR-181717?style=flat-square&logo=github&logoColor=white)](https://github.com/bosskmk/pluto_grid/pull/1165)

**"fix: notify listeners on setConfiguration and setTextDirection changes"**

**Root cause found:** `setConfiguration()` and `setTextDirection()` updated the grid's internal state but never called `notifyListeners()`, so `PlutoStateWithChange`-based cells (Select, Date, directional icons) silently kept rendering stale configuration until an unrelated event happened to trigger a rebuild — most visibly, changing the app language appeared to only partially update the grid.

**Fix:** Added listener notification to both methods, using two different strategies to respect Flutter's build lifecycle — a direct `notifyListeners()` call for `setConfiguration()` (safe outside the build phase), and a deferred `notifyListenersOnPostFrame()` for `setTextDirection()` (called mid-build from `PlutoGridLayoutDelegate`, where a direct call would trip Flutter's build-phase assertions). The deferred pattern mirrors the package's existing `setKeepFocus()` convention for consistency.

**Impact:** The fix is centralized in the package itself, so every application using `pluto_grid` benefits — RTL/LTR switches and configuration changes now propagate to every dependent cell immediately, with no manual refresh. Includes new unit tests covering both notification paths and passed the maintainer's Copilot-assisted review round.
